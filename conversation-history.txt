[Me — audit first]
Read every source file, both prior migrations, and the deployment config before
writing anything. Three findings changed the plan:

  1. Migration 20260729180000_platform_features.sql had NEVER been applied. The
     live database contained only `profiles` and `user_roles` — no live_streams, no
     iwitness_reports, no training tables. Verified via the Supabase Management API:
       select table_name from information_schema.tables where table_schema='public'
       -> [profiles, user_roles]
     So "LiveKit integration", "i-Witness storage" and "DIGEO training" had no
     backing schema at all; the UI was hard-coded arrays and sample MP4s.

  2. Admin RLS could never be satisfied. Migration 20260729171455 revoked EXECUTE on
     has_role(uuid, app_role) from `authenticated`, but the user_roles admin policies
     call exactly that function. Proved it by impersonating the Super Admin:
       begin; set local role authenticated;
       set local "request.jwt.claims" = '{"sub":"3bd3...","role":"authenticated"}';
       select count(*) from public.user_roles;
       -> ERROR 42501: permission denied for function has_role
     The Users & Roles screen could only ever see the caller's own rows.

  3. The app is a client-only SPA. vite.config.ts has the router plugin but NOT the
     TanStack Start plugin, and vercel.json builds to dist/ with SPA rewrites. So
     createServerFn cannot work — my first attempt at server-side Places/LiveKit
     proxies failed the build with:
       Error: Missing "#tanstack-start-entry" specifier in "@tanstack/start-server-core"
     Rather than convert the deployment to SSR (which the user had only just
     stabilised on Vercel), I moved both secret-holding proxies to Supabase Edge
     Functions and kept the SPA build untouched.
